# 海外保固與售後：討論稿

**這是討論稿，不是定案，還沒有任何程式。** 請連同 `給AI的指示.md` 一起交給你的 AI，從第 5 節「待決定事項」的 🔴 題開始，一題一題談，結論填回第 5 節的「決定」欄。

## 1. 要做什麼

在全球保固網站的**海外頁**提供三件事：

```
保固與售後
├─ A 保固登錄
├─ B 查詢保固
│   └─ 輸入登錄的 Email ─ 一鍵申請維修／聯絡售後 ─ 留下問題和聯絡方式 → 寄到客服信箱
└─ C 申請維修／聯絡售後
    └─ 留下問題和聯絡方式 → 寄到客服信箱
```

## 2. 流程

| 功能 | 客人做什麼 | 系統做什麼 |
|---|---|---|
| **A 保固登錄** | 填姓名、Email、產品、購買通路、訂單編號、購買日期 | 檢查格式 → 存入 → 給登錄編號 |
| **B 查詢保固** | 輸入登錄的 Email（可能還要驗證，見 Q3）→ 看到自己的產品與保固到期日 → 可按「一鍵申請維修」 | 只回傳**這位客人自己的**資料；查不到就引導去 C |
| **C 申請維修／聯絡售後** | 填問題與聯絡方式（從 B 進來則產品已自動帶入） | 檢查 → **先存案件**（給案件編號）→ 寄信到客服信箱（客服按回覆就回到客人）→ 告訴客人「已收到」 |

**做完的標準**：客人用英文手機就能完成；別人無法猜出他人資料；寄信失敗案件不會消失；不能被拿來大量寄垃圾信；不影響台灣頁與 ERP。

## 4. 工程端草案（可以推翻）

**建議上線順序**：① C 申請維修（客人最急、不依賴保固規則）→ ② A 海外登錄（取代舊網站）→ ③ B 查詢保固（依賴最多）。

**資料**：只新增 `warranty_` 開頭的資料表。登錄表增加「國家」「序號（選填）」；新增案件表（案件編號、姓名、Email、國家、產品、問題、狀態：已寄出／寄信失敗…）。防護同登錄表：公開訪客完全不能讀寫，只有網站伺服器端能寫。

**寄信**：用寄信服務（候選 Resend、SendGrid、Amazon SES 或公司郵件主機），寄件人用本站網域（需設定 SPF／DKIM，要有人能改 DNS），信件用純文字，Reply-To 設為客人 Email。

**查詢保固的驗證方式**（最重要的安全決定）：

| 選項 | 安全度 | 說明 |
|---|---|---|
| L1 只輸入 Email | ❌ 低 | 知道別人 Email 就看得到對方買了什麼，**不建議** |
| L2 登錄編號＋Email | 中 | 客人常忘記編號 |
| L3 Email 驗證碼 | 高 | 需要寄信功能（階段 1 反正要做）。查不到時一律顯示相同訊息，避免被探測 |

**防濫用**：隱藏欄位（已有）＋送出次數限制＋真人驗證（例如 Cloudflare Turnstile）。

## 5. 待決定事項

🔴 = 卡關，沒決定就無法開工。「建議」是工程端初步想法，可以不同意。

| 題 | 要決定什麼 | 建議 | 決定 |
|---|---|---|---|
| Q1 🔴 | 客服信箱地址？海外統一一個還是依地區分？誰收、誰回？ | 先統一一個，量大再拆 | |
| Q2 🔴 | 保固規則：期限幾年？從購買日還是登錄日起算？各產品、各地區一樣嗎？條款文案誰提供、有英文版嗎？ | 先全產品全地區同一期限、購買日起算 | |
| Q3 🔴 | 查詢保固的驗證方式（L1／L2／L3） | L3；寄信沒準備好先 L2；不採 L1 | |
| Q4 | 查到後顯示哪些欄位？ | 只顯示產品、購買日、到期日、狀態；不顯示姓名、完整 Email、訂單編號 | |
| Q5 | 登錄要不要核對訂單、誰核對？（Amazon 等海外訂單網站無法自動驗證） | 登錄即生效；申請維修時才要求購買證明 | |
| Q6 | 海外登錄要加哪些欄位（國家、序號）？海外通路清單有哪些？ | 國家必填、序號選填；通路請業務列出實際在賣的 | |
| Q7 🔴 | 維修表單欄位：姓名、Email、國家、產品、序號、問題描述、其他聯絡方式、照片… 各必填／選填／不收？ | 姓名／Email／國家／產品／問題 必填；序號、電話選填；**照片先不收** | |
| Q8 | 案件只寄信，還是先存再寄？ | 先存再寄（寄失敗也找得回來，有案件編號） | |
| Q9 🔴 | 用哪家寄信服務？寄件網域？費用與帳號誰管？ | 選免費額度、設定簡單的服務，用正式網域 | |
| Q10 | 要不要寄確認信給客人？ | 只寄案件確認；登錄確認視 Q3 | |
| Q11 | 語言：只英文，還是加日文、德文等？ | 先只做英文 | |
| Q12 🔴 | 隱私政策、客人是否要勾選同意、資料保存多久、刪除怎麼處理、誰負責確認（法務） | 至少放隱私政策連結；其餘請負責人確認 | |
| Q13 | 舊系統（Johnny／WordPress）的保固資料要不要匯入？何時切換？ | 先確認舊資料筆數與格式再決定 | |
| Q14 | 防濫用要做到什麼程度？ | 隱藏欄位＋次數限制＋真人驗證都加 | |
| Q15 | 要不要和 ERP 訂單比對？ | 先不連動（海外訂單多半不在 ERP） | |
| Q16 | 誰看登錄與案件？用什麼看？ | 階段 1 只靠客服信箱；案件變多再做唯讀後台 | |
| Q17 | 對客人承諾的回覆時效、客服時間與時區 | 寫保守的工作日時效 | |
| Q18 | 同意第 4 節的上線順序嗎？有沒有哪個必須先上？ | C → A → B | |

## 6. 不能違反的限制

1. **網站與公司 ERP 完全隔離**：網站沒有 ERP 的金鑰、連不到 ERP 資料。要互通只能由 ERP 單向送資料過來。
2. **客人資料只有他自己能看**，任何頁面都不能讓人瀏覽他人資料。
3. **客人輸入的內容一律不可信**（當純文字處理）。
4. **寄信功能必須防濫用**，否則會被拿來寄垃圾信、灌爆客服信箱。
5. **密鑰不寫進文件、不貼給 AI**。
6. **個資**（姓名、Email）涉及海外各地法規，這份文件**不是法律意見**，需由負責人或法務確認（Q12）。
