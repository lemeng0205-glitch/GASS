# 查詢保固＋線上諮詢維修：流程與規格

**給誰看**：負責做海外保固頁面的海外業務，以及他使用的 AI。請整份交給 AI 一起讀。
**前提**：保固登錄（功能 A）已上線（`public/warranty/`，資料存業務的 Google 試算表，由 `Code.gs` 接收）。本文件接著做 **B 查詢保固**、**C 線上諮詢維修**。
**先讀**：`整合指南.md`（限制與外觀）、`海外保固_交接說明.md`（你自己寫的）、`..\海外保固\海外保固_討論稿.md`（Q 編號指那份的第 5 節）。

---

## 1. 客人看到的流程（一張圖）

```
全球服務中心（海外頁）
   │
   ├─ 保固登錄 ───────────────→ 登錄完成畫面 ─┬→「Check my warranty」
   │                                           └→「Contact support」
   │
   └─ 「Warranty & Support」入口頁（新）
         ├─ ① Check my warranty（查詢保固）
         │     輸入 Email → 收到 6 位數驗證碼 → 輸入驗證碼
         │       ├─ 找到：顯示「我的產品清單」＋保固狀態
         │       │         └─ 每個產品旁「Request repair / support」→ 進 ② 且產品已自動帶入
         │       └─ 找不到：顯示固定訊息（見 §5）→「Register now」或「Contact support」
         │
         └─ ② Contact support（線上諮詢維修）
               填問題 → 送出 → 畫面顯示案件編號 → 客人收到確認信
               客服用信箱回覆（回覆直接回到客人）
```

三個入口都可以直接進 ②，**不一定要先查詢**（沒登錄過、忘記 Email 的客人也要能求助）。

## 2. 頁面清單（全部放 `public/warranty/`，沿用現有樣式與 CSP 規則）

| 檔案 | 用途 |
|---|---|
| `support.html` | 入口頁：兩張卡片「Check my warranty」「Contact support」 |
| `lookup.html` | ① 查詢保固（三步：Email → 驗證碼 → 結果） |
| `case.html` | ② 諮詢維修表單；網址可帶 `?product=…&reg=EWxxxxxxxx`（從查詢結果進來時自動帶入，且帶驗證通行證，見 §4） |
| `warranty.css` | 共用，不要另開一份新樣式 |
| 頁首 | 與現有 `index.html` 相同（eiP logo 回 `/country/intl`） |

頁面不能有行內 `<script>`、`<style>`、`style=""`（嚴格 CSP）。圖示、標題、分享預覽比照 `index.html`。

## 3. 欄位

### ① 查詢保固
| 步驟 | 欄位 | 規則 |
|---|---|---|
| 1 | Email | 必填，格式檢查 |
| 2 | 6 位數驗證碼 | 必填，只收數字；可按「Resend」（60 秒後才能再按） |
| 3 | （結果）每個產品顯示：產品名稱、購買日、保固到期日、狀態標籤 | **不顯示**姓名、完整 Email、訂單編號、序號全碼（序號只顯示後 4 碼） |

### ② 諮詢維修（案件表單）
| 欄位 | 必填 | 說明 |
|---|---|---|
| Full name | ✅ | 從查詢進來可預填，仍可改 |
| Email | ✅ | 同上；客服回覆寄到這裡 |
| Country / Region | ✅ | 下拉，同登錄頁的 13 國 |
| Product | ✅ | 下拉，同登錄頁；從查詢進來自動選好 |
| Serial number | 選填 | |
| Issue type | ✅ | 下拉：Not working / Charging or connection problem / Physical damage / Missing parts / Other |
| Describe the problem | ✅ | 多行，上限 1000 字 |
| Phone / WhatsApp | 選填 | 另一種聯絡方式 |
| Proof of purchase | **不收檔案** | 頁面提示：「Our team may ask you to reply with a photo of your receipt or order page.」（Q7：照片先不收，避免檔案上傳的風險） |
| 同意隱私政策 | ✅ | 同登錄頁 |
| 隱藏欄位 | — | 同登錄頁（防機器人） |

## 4. 系統流程（用現有的 Apps Script ＋ Google 試算表做法）

Apps Script 一支程式用 `action` 區分動作，沿用登錄頁的送法（`POST`、`text/plain`、JSON 字串；回 `{ok:true,…}` 或 `{ok:false,error}`）。

### 試算表分頁
| 分頁 | 欄位 | 備註 |
|---|---|---|
| `registrations`（已有） | 沿用，**新增** `warranty_end`（日期） | 登錄時算好：購買日＋期限（見 §6）。舊資料用公式或腳本補 |
| `cases`（新） | `case_id, submitted_at, name, email, country, product, serial_no, issue_type, description, phone, reg_id, verified(yes/no), status, source, notification` | 案件編號 `EC`＋8 碼英數（與登錄編號同一組字元，不含 0 O 1 I）。`status` 預設 `new` |
| `lookup_codes`（新） | `email_hash, code_hash, expires_at, attempts, used` | **驗證碼不存明碼**（存雜湊）；過期資料定期清除 |

### 動作
| action | 傳入 | 做什麼 | 回傳 |
|---|---|---|---|
| `lookup_request` | `email` | 檢查格式與頻率 → **不論找不找得到都回成功** → 只有該 Email 在 `registrations` 找得到時才寄 6 位數驗證碼（10 分鐘有效，用 `service-us` 寄出） | `{ok:true}`（永遠一樣，避免被拿來探測誰有登錄） |
| `lookup_verify` | `email, code` | 比對雜湊；錯誤累計，5 次鎖定該驗證碼；通過後回傳該 Email 的產品清單與一張**通行證** `token` | `{ok:true, items:[…], token}`；失敗 `{ok:false,error:'code'}` |
| `case_create` | 案件欄位，可帶 `token` | 驗證欄位 → **先寫入 `cases`**（含案件編號）→ 寄信給客服（Reply-To＝客人）→ 寄確認信給客人 → 結果寫回 `notification` 欄 | `{ok:true, case_id, email_sent}` |

**通行證 `token`**：Apps Script 用 `Script Properties` 裡的祕密字串做 HMAC 簽章，內容含 Email 與到期時間（15 分鐘）。`case_create` 帶有效 token → `verified=yes`，客服知道 Email 是本人驗證過的；沒帶 → `verified=no`（照樣收案，但客服要多確認身分）。**祕密字串不寫在程式碼裡、不寫在文件裡、不貼給 AI。**

### 客服收到的信（寄到客服信箱）
- 主旨：`[EC12AB34CD] Repair request – eiP Pencil X – United States`
- 內文（純文字）：案件編號、驗證狀態（verified / not verified）、姓名、Email、國家、產品、序號、問題類型、問題描述、電話、登錄編號（若有）。
- **Reply-To 設為客人 Email**，客服直接按回覆。
- 客人輸入的內容一律當純文字，不放進 HTML 標籤、不放進主旨以外的標頭。

### 客人收到的確認信
固定內容、**不含客人輸入的文字**（避免被拿來寄垃圾信）：案件編號、「We have received your request and will reply by email within X business days.」、客服信箱、IG 連結。樣式沿用登錄確認信（`Code.gs` 的 `htmlBody_`）。

## 5. 狀態與固定訊息

### 保固狀態標籤
| 條件 | 標籤 | 顯示 |
|---|---|---|
| 今天 ≤ 到期日 | **Active** | Covered until 2027-03-15 |
| 今天 > 到期日 | **Expired** | Expired on 2026-03-15 |
| 找不到 | — | 見下 |

### 找不到時（Email 沒登錄過，或驗證碼拿不到）
`lookup_request` 因為要避免探測，**畫面一律顯示**：
> If this email is registered, we have sent a 6-digit code to it. The code is valid for 10 minutes.

並且在這句下面**永遠**放兩個連結：「Haven't registered? Register now」「Need help? Contact support」。客人收不到信就點 Contact support，不會卡死。

### 案件狀態（`cases.status`，客服手動改）
`new` → `in_progress` → `waiting_customer`（等客人補資料）→ `resolved`／`closed`。目前客人**看不到**案件狀態，只靠信件往來（Q16：案件多了再做查案件頁）。

## 6. 保固規則（⚠ 要先決定，見 §9）

暫定（請負責人確認）：**一年功能性保固（確認信已經這樣寫）、從購買日起算**，所有產品、地區相同。
`warranty_end = purchase_date + 1 年`；Apps Script 登錄時就寫入，查詢時直接讀，不要在前端自己算。

## 7. 客服作業流程（給海外業務與客服）

1. 客服信箱收到案件信 → 先看「verified」。
2. **未驗證**或**沒有登錄編號**：回信請客人提供購買證明（訂單頁截圖或收據）；收到前不承諾保固。
3. **已驗證且在保固內**：回信說明處理方式（排障步驟／寄回流程／換貨）。
4. **已過保**：回信說明付費維修或處理選項（若無此服務，禮貌說明）。
5. 回覆時**保留主旨裡的案件編號**，方便之後搜尋。
6. 處理結果記在試算表 `cases` 的 `status` 欄。
7. 時效：先寫保守承諾（例如 2 個工作日內回覆）；實際時效請負責人決定（Q17）。
8. 客人要求刪除個資時：依隱私政策的做法，在三個分頁刪除該 Email 的所有列。

## 8. 安全規則（不能省）

1. **查詢一定要驗證**：不接受「只輸入 Email 就顯示資料」（Q3：L1 不採用）。
2. **不洩漏誰有登錄**：`lookup_request` 永遠回相同結果，回應時間也盡量一致。
3. **驗證碼**：6 位數隨機、10 分鐘有效、只能用一次、錯 5 次作廢；試算表只存雜湊。
4. **頻率限制**：同一 Email 每小時最多 3 次索取驗證碼；全站每小時登錄＋查詢＋案件各設總量上限（沿用 `overLimit_` 做法，分開計算，避免互相擠掉）。
5. **回傳最少欄位**：查詢結果只給產品、購買日、到期日、序號後 4 碼；不回姓名、完整 Email、訂單編號。
6. **輸入一律當純文字**：開頭是 `= + - @` 的字串前面加單引號（沿用 `safe_`）；信件內容不放 HTML。
7. **寄信防濫用**：寄給客人的確認信內容固定；一個 Email 每天最多收到 5 封系統信。
8. **Apps Script 寄信額度**：個人 Gmail 每天約 100 封、Workspace 約 1500 封，驗證碼＋確認信＋客服信**都算**。請先確認帳號類型與預估量；量大要改用專業寄信服務（Resend／SES 等，見討論稿 Q9）。
9. **沒有真人驗證前**：公開的接收網址可能被灌爆，請至少把上面第 4、7 點做好；建議之後加 Cloudflare Turnstile（要放行 `https://challenges.cloudflare.com`，並同步通知負責人調整 CSP）。
10. **金鑰、祕密字串、`.env` 內容**：不貼進對話、文件、程式碼；需要新的環境變數或設定，列出名稱交給負責人。
11. **不碰 ERP、不碰台灣頁**。

## 10. 上線順序與驗收

建議順序（討論稿 Q18）：**C（案件表單）→ B（查詢保固）**。C 不依賴保固期限規則，客人最急；B 需要先決定 §9 的 Q2。

### 驗收清單
- [ ] 手機（英文）：從入口頁到送出案件、從查詢到申請維修，全程能完成。
- [ ] 嚴格 CSP 下主控台沒有任何違規；`?demo` 模式不寄信、不存資料。
- [ ] 查一個**沒登錄**的 Email：畫面訊息與查**有登錄**的 Email 完全相同。
- [ ] 驗證碼：錯 5 次作廢、10 分鐘過期、重送有 60 秒間隔、用過不能再用。
- [ ] 查詢結果沒有姓名、完整 Email、訂單編號。
- [ ] 案件：先存入 `cases` 再寄信；故意讓寄信失敗，案件仍在表裡且 `notification` 標失敗。
- [ ] 客服信的 Reply-To 是客人；按回覆直接寫給客人。
- [ ] 跳過網頁直接對接收端送垃圾資料（不在清單的國家、錯誤 Email、超長文字）：全部被拒絕、不寫入。
- [ ] 欄位內容以公式字元開頭（`=1+1`）：以純文字儲存。
- [ ] 台灣頁、首頁、`/m/` 說明書頁、ERP 沒有任何變化。
- [ ] 沒有寫死網域、金鑰、祕密字串。
- [ ] 完成後回報負責人：入口頁網址，以及要掛到哪些選單（海外頁「保固登錄」旁的新卡片、登錄完成畫面的按鈕）。

## 11. 將來搬進公司資料庫

三個 action 的請求與回應格式照上面不變；之後只要把 `warranty.js` 設定區的 `endpoint` 換成本站 API，並把 `registrations`／`cases`／`lookup_codes` 改成 `warranty_` 開頭的資料表（SQL 放 `docs\sql\`，編號接 `011` 之後）即可，頁面不用重寫。
